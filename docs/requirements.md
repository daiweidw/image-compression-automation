# 本地图片压缩管理工具需求文档

## 1. 文档信息

- 项目名称：本地图片压缩管理工具（暂定）
- 文档类型：产品需求文档 / AI 实施规格
- 当前版本：v2.0（可分享桌面版）
- 关联文档：[技术实现架构](./technical-architecture.md)
- 运行形态：macOS 桌面应用（保留本地 Web 兼容模式）
- 核心压缩服务：TinyPNG / Tinify API
- 目标用户：需要在本机批量管理和压缩图片的个人用户

### 1.1 第二版交付基线

本版本在首版压缩闭环上完成桌面化与 P1 增强。本文后续仍保留首版需求细节，若与本节冲突，以本节为准。

- 交付独立 Electron `.app`，使用者无需安装 Node.js、pnpm 或工程源码。
- 生成 Apple Silicon（arm64）Ad Hoc 签名 ZIP，不制作 Intel 或 universal 包。
- 每位使用者在应用内填写自己的 TinyPNG API Key；发布者不提供共享 Key，也不承担他人的 API 额度。
- 因发布者没有付费 Apple Developer 账号，本版本只进行 Ad Hoc 临时签名，不进行 Developer ID 签名或公证，不上架 App Store，不提供自动更新。
- 接收者解压后首次通过 Finder 右键应用并选择“打开”；必要时在“系统设置 → 隐私与安全性”中选择“仍要打开”。系统策略可能继续拦截未公证应用，文档不保证所有目标 Mac 均可批准，也不引导关闭 Gatekeeper 或执行绕过系统安全的命令。
- 桌面版为单实例，关闭主窗口或点击页面“退出应用”都会停止内嵌本地服务。

### 1.2 第二版新增范围

- 自动监听原图目录，新增、修改、删除图片后增量刷新列表。
- 自动压缩是独立开关且默认关闭；仅对监听期间新加入的受支持图片生效，开启时明确提示会消耗 TinyPNG 次数。
- 原图与压缩结果支持滑块对比和并排对比，并提供缩放、平移和重置。
- 桌面版使用 Electron `safeStorage` 加密保存 API Key，加密能力由 macOS Keychain 保护；旧明文密钥文件首次启动时自动迁移并删除。
- 使用系统原生目录选择器，并可在 Finder 中打开结果目录或显示结果图片。
- 支持暂停、继续任务；应用重启后，尚未开始的任务进入“等待恢复”，必须由用户确认后继续。
- 支持分页、筛选的任务历史。
- 输出冲突策略可选择覆盖本工具结果、跳过已有文件或添加 `compressed` 后缀。
- 图片列表使用虚拟滚动，缩略图按源文件 SHA-256 缓存到磁盘。

### 1.3 第二版明确不做

- 不提供团队共用 TinyPNG Key、代理额度、账号系统或云端服务。
- 不自动重试应用重启时已经上传中的任务，避免重复扣除 TinyPNG 次数。
- 不支持 Intel Mac、Windows/Linux 安装包、多工作区、格式转换、本地压缩引擎和无人值守规则。
- 不提供 Developer ID 签名、公证、安装器、增量更新或应用内自动更新；Ad Hoc 签名只用于保证应用包内部完整性。

## 2. 需求背景

用户日常会把待压缩图片放入某个本地文件夹。目前使用 TinyPNG 网站时，需要逐个上传、等待处理并手动下载，且不容易看出本地图片中哪些已经压缩、哪些仍待处理。

本项目需要提供一个运行在本机的管理页面。用户通过浏览器查看指定原图目录中的图片，识别每张图片的压缩状态，选择一张或多张图片交给 TinyPNG 压缩，并让程序自动把结果保存到另一个指定的本地目录。

## 3. 对需求的理解

本项目不是重新实现图片压缩算法，而是为 TinyPNG API 提供一个本地可视化工作台。

核心流程如下：

1. 用户启动本地程序，并在浏览器打开本地管理页面。
2. 用户配置原图目录、压缩结果目录和 TinyPNG API Key。
3. 程序扫描原图目录，在页面中展示所有受支持的图片及其压缩状态。
4. 用户选择单张或多张未压缩、已过期或压缩失败的图片，并发起压缩。
5. 本地后端读取原图，通过 TinyPNG API 完成压缩。
6. 程序将压缩结果自动写入结果目录，并记录本次处理信息。
7. 页面实时更新状态、压缩前后大小、节省空间和错误信息。

这里的“是否已经压缩过”不能只依赖文件名判断。系统应维护一份本地处理记录，并结合原文件内容指纹、输出文件是否存在等信息判断状态。当原图内容发生变化时，即使名称不变，也应重新标记为“待压缩”。

## 4. 产品目标

### 4.1 核心目标

- 在浏览器中清晰查看原图目录中的全部图片。
- 准确显示每张图片当前是否需要压缩。
- 支持选择单张或多张图片进行压缩。
- 自动调用 TinyPNG，并将结果保存到指定结果目录。
- 原图与结果目录均可由用户手动配置。
- 保留可追溯的本地压缩记录，避免无意义的重复压缩。

### 4.2 非目标（MVP 不做）

- 不自行实现或训练图片压缩算法。
- 不提供公网部署、多用户登录或团队权限体系。
- 不与云盘、对象存储、CMS 等外部系统同步。
- 不提供复杂的在线图片编辑、裁剪、水印或滤镜功能。
- 不监控整个磁盘，只处理用户明确指定的原图目录。
- 不默认自动压缩新文件；MVP 由用户在页面中手动发起。

## 5. 术语与状态定义

### 5.1 术语

- 原图目录：用户放置待处理图片的本地目录，只作为输入来源。
- 结果目录：保存 TinyPNG 返回结果的本地目录。
- 相对路径：图片相对于原图目录的路径。例如原图为 `/source/products/a.png`，其相对路径为 `products/a.png`。
- 文件指纹：根据原文件内容计算的哈希值，用于识别同名文件是否发生变化。建议使用 SHA-256。
- 压缩记录：程序保存的处理元数据，包括原图指纹、输出路径、压缩前后大小、处理时间和结果等。

### 5.2 图片状态

每张图片在任一时刻只能有一个主状态：

| 状态 | 含义 | 是否允许发起压缩 |
| --- | --- | --- |
| 待压缩 | 从未成功压缩，或没有可验证的成功记录 | 是 |
| 排队中 | 已加入本次任务，等待 API 调用 | 否 |
| 压缩中 | 正在上传、压缩或下载 | 否 |
| 已压缩 | 原图指纹与成功记录一致，且结果文件存在 | 可重新压缩，但需二次确认 |
| 原图已更新 | 文件名不变，但内容指纹与上次成功记录不同 | 是 |
| 结果缺失 | 有成功记录，但结果文件已被移动或删除 | 是 |
| 压缩失败 | 最近一次处理失败 | 是 |
| 不支持 | 文件扩展名或文件内容不受支持 | 否 |

状态判定优先级建议为：处理中状态 > 不支持 > 原图已更新 > 结果缺失 > 已压缩 > 压缩失败 > 待压缩。

## 6. 用户场景

### 6.1 首次使用

1. 用户启动应用。
2. 浏览器自动打开或用户手动访问本地地址。
3. 页面提示完成初始设置。
4. 用户填写或选择原图目录、结果目录，并配置 TinyPNG API Key。
5. 系统校验目录和 API Key。
6. 校验通过后扫描原图并进入图片列表。

### 6.2 压缩单张图片

1. 用户在图片列表找到目标图片。
2. 用户查看缩略图、状态、路径和文件大小。
3. 用户点击该图片的“压缩”操作。
4. 页面显示进行中状态与进度阶段。
5. 成功后页面显示结果大小、节省比例、保存位置和完成时间。

### 6.3 批量压缩

1. 用户通过复选框选择多张可压缩图片，或选择“全部待压缩”。
2. 页面显示已选择数量和预计消耗的 API 压缩次数。
3. 用户确认后提交任务。
4. 系统按受控并发逐张处理，并持续更新每张图片的状态。
5. 部分图片失败时，其余任务继续；任务结束后展示成功与失败汇总。

### 6.4 原图更新后重新压缩

1. 用户用新内容覆盖已有原图文件。
2. 用户刷新列表或重新扫描。
3. 系统通过文件指纹发现变化，标记为“原图已更新”。
4. 用户再次压缩，新结果覆盖该相对路径下的旧结果。
5. 系统更新压缩记录。

## 7. 功能需求

### 7.1 本地应用启动

- 应用必须启动一个仅供本机访问的 HTTP 服务，默认绑定 `127.0.0.1`，不得默认监听局域网或公网地址。
- 默认端口可使用固定值；端口被占用时，应选择可用端口并在启动信息中明确显示访问地址。
- 应提供简单、明确的一条启动命令。
- macOS 首版应提供一个可从 Finder 双击运行的启动入口。重复双击不得创建多个服务实例；应用已经运行时应打开现有页面。
- 应支持正常退出；退出时不得破坏已完成的结果文件和压缩记录。
- 浏览器页面应提供“退出应用”按钮。该操作必须停止本地服务，而不只是关闭浏览器标签页。
- 有排队或运行任务时，退出前必须展示任务数量并取得明确确认；不得静默中断任务。
- 服务停止后页面应显示“应用已退出，可以关闭此页面”。浏览器安全限制导致页面无法自动关闭是可接受行为。
- 意外退出后再次启动，已成功完成的图片仍应显示为“已压缩”。

### 7.2 设置管理

设置页面至少包含：

- 原图目录。
- 结果目录。
- TinyPNG API Key 输入入口。
- 是否递归扫描子目录，MVP 默认开启。
- 同时压缩数量，MVP 默认值建议为 2，可限制在 1 至 5。

设置行为：

- 原图目录和结果目录支持手动输入绝对路径。
- 如所选技术可可靠调用系统目录选择器，可同时提供“选择目录”按钮；手动输入必须始终可用。
- 保存前校验原图目录是否存在、是否为目录、是否可读。
- 结果目录不存在时，应明确询问或提示将创建目录；经用户确认后创建。
- 校验结果目录是否可写。
- 禁止原图目录与结果目录完全相同。
- 禁止结果目录位于原图目录内部，避免扫描到压缩结果并产生循环处理。
- 原图目录位于结果目录内部也应警告，建议视为无效配置。
- 路径校验失败时不得开始扫描或压缩，并显示具体原因。
- 设置保存后立即重新扫描。
- 用户必须能够直接在浏览器设置页面中填写、测试、更换和删除 TinyPNG API Key，无需手动修改代码或环境变量。
- API Key 使用密码型输入框，默认隐藏，并提供“显示/隐藏”控制；页面应提示该 Key 只会交给本机服务使用。
- 首次尚未配置时，输入框为空并明确显示“未配置”。未配置有效 Key 时，不允许发起压缩。
- 已保存时，页面只显示“已配置”和脱敏提示，不得从后端取回完整 Key，也不得把虚假的掩码字符当作 Key 再次提交。
- 编辑其他设置时，如果 API Key 输入框留空，默认表示保留现有 Key；更换 Key 时必须输入新值并重新校验。
- 删除 API Key 必须通过独立的“删除 API Key”操作并二次确认，不能因普通表单留空而误删。
- 点击“测试连接”时，将当前输入的新 Key 或已保存的 Key 交给本机后端验证；成功后显示“连接成功”，失败时显示可理解的原因。
- Key 保存动作必须由用户明确触发。测试新 Key 不应自动替换已保存的 Key，除非用户随后点击保存。
- API Key 从浏览器提交到本机后端后，只能保存在后端。优先使用操作系统凭据存储；如技术条件不允许，可使用仅当前用户可读的本地配置文件。不得写入 Git 跟踪文件、前端源码或浏览器持久化存储。
- API Key 不得在日志、后端返回内容或错误提示中明文输出。前后端仅通过本机地址通信，MVP 不得监听局域网或公网地址。
- 测试或调用 API 后，尽可能显示账户本月已用额度；若官方接口或 SDK 无法独立查询，则在第一次 API 调用后展示可获得的信息。

### 7.3 目录扫描

- 扫描原图目录及其子目录，是否递归由设置控制。
- MVP 支持 TinyPNG 当前 API 支持且项目已验证的图片格式，目标格式为 PNG、JPEG/JPG、WebP 和 AVIF。
- 格式支持必须以 TinyPNG 官方 API 的实际能力和返回结果为准；开发时应再次核对官方文档。
- 忽略隐藏文件、系统临时文件和结果目录。
- 应通过文件扩展名初筛，并在处理前校验真实文件类型，避免将伪装扩展名上传到 API。
- 单个文件无法读取时，不应导致整个扫描失败；该文件应显示错误状态或被记录到扫描警告中。
- 提供“重新扫描”按钮。
- 扫描期间显示加载状态，完成后显示图片总数及各状态数量。
- 扫描应能处理中等规模目录。MVP 验收基准：1,000 张图片时页面仍可正常交互，不因一次性生成全部原图大图而明显卡死。
- 缩略图应按需加载，不能将原图完整内容一次性内嵌到列表接口中。

### 7.4 图片列表与预览

主页面至少展示：

- 图片缩略图。
- 文件名。
- 相对路径。
- 图片格式。
- 像素尺寸（宽 × 高）。
- 原图文件大小。
- 当前状态。
- 最近压缩时间。
- 压缩后大小。
- 节省的字节数和百分比。
- 单图操作入口。

列表能力：

- 支持表格或紧凑网格视图，默认优先保证大量图片时易于浏览和选择。
- 支持按文件名或相对路径搜索。
- 支持按状态、格式筛选。
- 支持按文件名、原图大小、更新时间、压缩时间、节省比例排序。
- 支持分页或虚拟滚动，避免图片较多时页面性能显著下降。
- 支持单选、多选、选择当前筛选结果中的全部可压缩图片，以及清空选择。
- 不可压缩状态的图片不得被加入任务。
- 点击缩略图可打开较大预览，并显示原图与压缩结果的基础信息；MVP 不强制实现像素级对比滑块。

### 7.5 压缩任务

- 支持单张压缩和批量压缩。
- 发起前应显示待处理图片数量。
- 已压缩图片若被再次选择，应提示这是重复压缩，并要求用户确认。
- 任务在本地后端执行，TinyPNG API Key 不得发送到浏览器端。
- 后端读取原图并调用 TinyPNG 官方 API 或官方 SDK。
- 成功取得压缩结果后，先写入结果目录中的临时文件；写入完整并校验成功后，再以原子方式替换目标文件，避免中途失败留下损坏文件。
- 默认保持原文件名、扩展名和相对于原图目录的子目录结构。
- 示例：原图 `/source/products/phone/a.png` 应保存为 `/output/products/phone/a.png`。
- 写入前自动创建所需的子目录。
- 默认覆盖同一路径下由本工具生成的旧压缩结果，但不得覆盖原图。
- 压缩成功后记录原图指纹、输入和输出大小、相对路径、输出路径、处理时间以及 API 返回的可用信息。
- 单张图片失败不得终止整个批次。
- 对网络超时、临时网络错误、HTTP 429 和服务端 5xx，可使用有限次数的指数退避重试；建议最多重试 2 次。
- 对无效 API Key、不支持格式、文件过大、额度耗尽等确定性错误不应盲目重试。
- 同一张图片不得同时启动两个任务。
- 页面刷新后，后端任务应继续执行；重新进入页面应恢复展示当前状态。
- MVP 可以不支持取消已经提交给 TinyPNG 的单次请求，但应支持取消尚未开始的排队任务。

### 7.6 结果与反馈

每张图片成功后展示：

- “已压缩”状态。
- 压缩前大小。
- 压缩后大小。
- 减少的大小。
- 节省比例，计算公式为 `(原图大小 - 结果大小) / 原图大小 × 100%`。
- 结果文件的完整路径或可复制路径。
- 完成时间。

批次结束后展示：

- 总任务数。
- 成功数量。
- 失败数量。
- 跳过数量。
- 累计压缩前大小、压缩后大小和节省空间。
- 失败图片及对应原因。

可提供“在文件管理器中显示结果目录”操作；如果实现该功能，必须只打开用户配置的结果目录，不执行任意外部命令。

### 7.7 压缩记录和状态持久化

- 处理记录必须持久化到本机，推荐使用 SQLite；简单 JSON 仅在能保证并发写入和异常恢复的情况下采用。
- 状态数据库或元数据应存放在应用数据目录，不污染原图目录和结果目录。
- 至少保存以下字段：

| 字段 | 说明 |
| --- | --- |
| source_relative_path | 原图相对路径，作为记录关联信息之一 |
| source_hash | 成功压缩时的原图 SHA-256 |
| source_size | 原图字节数 |
| source_mtime | 原图修改时间，用于快速预判是否需要重新计算哈希 |
| output_path | 结果文件完整路径 |
| output_size | 结果文件字节数 |
| status | 最近一次任务结果 |
| compressed_at | 最近成功时间 |
| error_code | 最近失败错误分类 |
| error_message | 可供用户理解的错误摘要 |

- 系统不得仅凭相对路径或结果文件存在就判断为“已压缩”。
- 推荐先比较大小和修改时间，仅在必要时计算哈希，以兼顾准确性和扫描性能。
- 用户修改配置目录后，应按目录配置隔离或重新关联记录，不能把另一个目录中的同名文件误判为已压缩。

### 7.8 错误处理

错误提示应使用用户可理解的语言，同时保留足够的诊断信息。至少覆盖：

- API Key 未设置或无效。
- TinyPNG 本月额度耗尽或请求受限。
- 网络断开、连接超时、DNS 或 TLS 错误。
- TinyPNG 服务异常。
- 文件格式不支持或内容损坏。
- 文件超过 TinyPNG 当前限制。
- 原图在任务期间被移动、删除或修改。
- 原图无读取权限。
- 结果目录无写入权限或磁盘空间不足。
- 输出路径冲突。
- 临时文件写入或替换失败。

错误消息不得包含 API Key。页面应对可恢复错误提供“重试”操作。

### 7.9 日志

- 记录应用启动、配置校验、扫描、任务开始、任务结束和错误。
- 日志中可以记录文件路径，但不得记录 API Key、授权头或完整敏感响应。
- 日志应写入本机应用数据目录，并设置大小或保留天数上限，避免无限增长。
- 页面可提供精简的最近任务记录；MVP 不要求完整日志查看器。

## 8. 页面与交互要求

### 8.1 主页面布局

建议结构：

1. 顶部工具栏：当前原图目录、重新扫描、设置入口。
2. 状态摘要：总图片数、待压缩、已压缩、异常数量、累计节省空间。
3. 搜索与筛选区：关键词、状态、格式、排序。
4. 批量操作栏：已选择数量、压缩、取消排队、清空选择。
5. 图片列表：缩略图、文件信息、状态、压缩信息、单图操作。
6. 任务反馈区域：当前进度和最近批次汇总。

### 8.2 设置页面或弹窗

- 将路径配置、API Key 和扫描选项集中呈现。
- 每一项在保存时显示明确校验结果。
- 修改目录会影响当前列表，保存前应提示将重新扫描。
- API Key 区域包含密码型输入框、“显示/隐藏”、“测试连接”、“保存/更换”和“删除 API Key”操作。
- 已配置状态不回填完整 Key，只显示“已配置”；用户输入新 Key 后才能执行更换。
- 显示功能只显示用户本次正在输入、尚未保存的内容，不得用于读取此前保存的完整 Key。
- 在页面附近简短说明图片将上传至 TinyPNG、Key 仅供本机后端调用。

### 8.3 视觉与可用性

- 定位为本地生产力工具，界面应紧凑、清晰，适合反复操作。
- 所有仅使用图标的按钮应有可访问名称和悬浮提示。
- 处理中、成功、警告、失败不能仅依赖颜色区分，还需图标或文字。
- 关键操作应有禁用状态，防止重复提交。
- 长文件名和长路径不得撑破布局，应截断展示并支持查看完整内容。
- 页面至少适配常见桌面浏览器宽度；MVP 不要求移动端完整体验。
- 应支持键盘焦点和基本无障碍操作。

## 9. 数据与文件规则

### 9.1 原图保护

- 工具对原图目录只读。
- 任何压缩、重试、失败恢复操作都不得修改、覆盖或删除原图。
- 系统不得自动删除压缩结果以外的用户文件。

### 9.2 输出命名

- 默认保持原始文件名和格式。
- 默认保持子目录结构。
- 文件名大小写按当前操作系统文件系统规则处理。
- 若两个源文件会映射到同一输出路径，系统必须在执行前报冲突，不能静默覆盖不相关文件。
- 输出格式转换不属于 MVP；例如 PNG 输入仍输出 PNG。

### 9.3 临时文件

- 临时文件必须位于结果目录或应用专用临时目录。
- 临时文件名应避免与用户文件冲突。
- 成功后清理临时文件。
- 应用启动时可清理本工具遗留且能明确识别的过期临时文件，但不能用宽泛规则删除其他文件。

## 10. 安全与隐私要求

- 服务默认仅绑定 `127.0.0.1`。
- 所有文件读取接口都必须限制在当前原图目录内，防止通过 `../` 等路径读取任意本机文件。
- 所有结果写入接口都必须限制在当前结果目录内。
- 浏览器只接收展示所需数据，不接收 TinyPNG API Key。
- 缩略图接口必须校验路径和允许的文件类型。
- API Key 不得提交到版本库。
- 应提供 `.gitignore`，忽略本地配置、数据库、日志、临时文件和环境变量文件。
- 需要在界面或 README 中说明：被压缩图片会上传至 TinyPNG 服务处理，用户应自行确认图片是否允许传给第三方服务。
- 不引入不必要的遥测；MVP 默认不收集或上传使用统计。

## 11. 非功能需求

### 11.1 兼容性

- 优先支持 macOS；代码结构应尽量避免阻碍后续支持 Windows 和 Linux。
- 支持当前主流版本的 Chrome 或 Edge；如使用非 Chromium 特有能力，应提供替代方案。
- 文件路径处理不得硬编码 `/`，应使用运行时提供的跨平台路径 API。

### 11.2 性能

- 1,000 张图片的目录扫描不应阻塞服务健康检查和设置页面操作。
- 列表首次响应不应携带所有图片的原始二进制内容。
- 哈希和尺寸读取等耗时工作应限制并发，避免大量占用 CPU、内存和文件句柄。
- 压缩并发必须可控，避免触发 API 限流。

### 11.3 可靠性

- 只有当结果文件完整落盘后，才能将记录标记为成功。
- 数据库更新和文件落盘顺序应避免产生“记录成功但结果文件不存在”的假状态；即使出现，也要在下次扫描标记为“结果缺失”。
- 批量任务允许部分成功。
- 服务重启后应重新校验压缩记录，不把中断中的任务误认为成功。

### 11.4 可维护性

- 前端展示、目录访问、任务调度、TinyPNG 客户端和持久化逻辑应分层。
- TinyPNG 调用封装为独立适配器，便于模拟测试和未来替换服务。
- 核心状态判定规则必须有自动化测试。
- 关键配置应集中定义，不能散落硬编码。

## 12. 建议技术方案（非强制）

由于普通网页不能在不受限制的情况下持续扫描和写入任意本地目录，本项目必须包含一个本地后端，不能只做纯静态网页。

建议采用：

- 前端：React + TypeScript + Vite。
- 本地后端：Node.js + TypeScript，使用 Fastify 或 Express。
- 数据存储：SQLite。
- 图片元数据：使用成熟图片解析库读取尺寸和格式。
- TinyPNG：优先使用官方 Node.js SDK；若 SDK 能力不足，再封装官方 REST API。
- 实时进度：MVP 可使用轮询；如已有成熟结构，可使用 Server-Sent Events。
- 测试：单元测试覆盖状态判定与路径安全，集成测试覆盖扫描和任务流程，浏览器端端到端测试覆盖主流程。

后端建议模块：

| 模块 | 职责 |
| --- | --- |
| config | 保存和校验目录、并发数等设置 |
| scanner | 扫描文件、读取元数据、计算或复用指纹 |
| record-store | 持久化压缩记录和任务状态 |
| compression-queue | 排队、并发控制、取消待执行任务 |
| tinypng-adapter | 调用 TinyPNG、分类错误、读取额度信息 |
| output-writer | 安全创建目录、写临时文件、原子替换 |
| local-api | 向浏览器提供受限的列表、缩略图、设置和任务接口 |

## 13. 建议本地 API 边界（非强制）

后续实现可按现有框架调整命名，但应保持等价能力：

| 方法与路径 | 用途 |
| --- | --- |
| `GET /api/health` | 判断本地服务是否正常 |
| `GET /api/settings` | 获取脱敏后的设置，只返回 API Key 是否已配置 |
| `PUT /api/settings` | 校验并保存设置；Key 留空时保留已有值 |
| `POST /api/settings/test-tinypng` | 测试当前输入或已保存的 Key，不回传密钥且不自动保存新 Key |
| `DELETE /api/settings/tinypng-key` | 二次确认后删除已保存的 API Key |
| `POST /api/scan` | 触发重新扫描 |
| `GET /api/images` | 分页、搜索、筛选和排序获取图片 |
| `GET /api/images/:id/thumbnail` | 获取受限尺寸的缩略图 |
| `GET /api/images/:id/preview` | 获取受控的预览内容 |
| `POST /api/compression-jobs` | 提交单张或批量压缩任务 |
| `GET /api/compression-jobs/:id` | 获取批次及各图片进度 |
| `POST /api/compression-jobs/:id/cancel` | 取消尚未执行的排队项 |
| `POST /api/images/:id/retry` | 重试单张失败图片 |

任何以图片 ID 访问文件的接口，都应由后端从受信任记录解析真实路径，不能直接接受浏览器传入的任意绝对路径。

## 14. 验收标准

### 14.1 初始配置

- Given 应用首次启动且尚未配置目录，When 用户打开页面，Then 页面明确引导用户设置原图目录、结果目录和 API Key。
- Given 尚未配置 API Key，When 用户打开设置页面，Then 页面提供可直接填写的密码型输入框、显示/隐藏和测试连接入口。
- Given 尚未配置有效 API Key，When 用户尝试压缩，Then 操作被阻止并引导至 API Key 设置入口。
- Given 用户填写不存在的原图目录，When 保存设置，Then 保存失败并显示“目录不存在”等具体原因。
- Given 结果目录位于原图目录内部，When 保存设置，Then 系统拒绝该配置并解释会造成循环扫描。
- Given API Key 已保存，When 用户重新打开设置，Then 页面显示“已配置”，但不得显示或回填完整明文密钥。
- Given API Key 已保存且用户编辑其他设置时留空 Key 输入框，When 保存设置，Then 原 API Key 保持不变。
- Given 用户输入新 API Key 并只点击测试连接，When 测试成功，Then 不自动覆盖此前保存的 Key。
- Given 用户选择删除 API Key，When 用户完成二次确认，Then 后端删除凭据且页面恢复“未配置”状态。

### 14.2 扫描和状态

- Given 原图目录包含支持格式和非图片文件，When 扫描完成，Then 列表只将受支持图片标记为可压缩，非目标文件不进入可压缩集合。
- Given 一张从未处理的图片，When 扫描完成，Then 状态为“待压缩”。
- Given 一张成功压缩且原图未变化、结果仍存在的图片，When 再次扫描，Then 状态为“已压缩”。
- Given 原图内容被替换但文件名未变，When 再次扫描，Then 状态为“原图已更新”。
- Given 成功记录仍在但结果文件被删除，When 再次扫描，Then 状态为“结果缺失”。

### 14.3 压缩与输出

- Given 用户选择一张待压缩图片，When TinyPNG 成功返回结果，Then 结果按相同相对路径保存到结果目录，原图保持不变。
- Given 原图位于多级子目录，When 压缩成功，Then 结果目录中创建相同层级的子目录。
- Given 用户选择多张图片且其中一张失败，When 批次结束，Then 其他图片继续处理，汇总准确显示成功和失败数量。
- Given 写入结果期间发生异常，When 任务失败，Then 不留下被当作成功结果的半成品文件。
- Given 用户刷新浏览器页面，When 后端任务仍在运行，Then 页面能够重新获取并显示任务进度。

### 14.4 安全与错误

- Given 浏览器请求包含路径穿越内容，When 请求预览或缩略图，Then 后端拒绝请求且不泄露原图目录外文件。
- Given API Key 无效，When 发起测试或压缩，Then 显示可理解错误，日志和前端响应中均不包含密钥。
- Given 网络暂时失败，When 请求符合重试条件，Then 系统有限重试并最终显示准确结果。
- Given 结果目录不可写，When 发起压缩，Then 任务在写入前或写入时明确失败，不修改原图。

### 14.5 页面体验

- Given 列表中有大量图片，When 用户搜索、筛选和滚动，Then 页面保持可操作，缩略图按需加载。
- Given 图片处于压缩中，When 用户重复点击压缩，Then 系统不会提交同一图片的并行重复任务。
- Given 文件名或路径很长，When 列表展示，Then 不破坏布局，并可查看完整值。

## 15. 自动化测试最低要求

### 15.1 单元测试

- 各压缩状态的判定逻辑。
- 原图哈希变化检测。
- 输入到输出的相对路径映射。
- 路径穿越防护。
- 原图与结果目录重叠检测。
- 节省比例计算。
- TinyPNG 错误分类及是否重试的规则。

### 15.2 集成测试

- 扫描包含子目录、损坏图片和无权限文件的测试目录。
- 使用假的 TinyPNG 适配器完成成功、失败、超时、限流和部分失败流程，不在常规测试中消耗真实 API 额度。
- 验证临时文件写入与原子替换。
- 验证服务重启后的记录恢复和状态重新判定。

### 15.3 端到端测试

- 首次配置并扫描目录。
- 搜索、筛选、选择并提交单张压缩。
- 提交批量压缩并查看汇总。
- 原图更新后重新扫描并再次压缩。
- 无效 API Key 和结果目录不可写的错误呈现。

## 16. 实施阶段建议

### 阶段一：项目骨架与设置

- 搭建本地前后端和统一启动方式。

### 阶段三：TinyPNG 压缩闭环

### 阶段四：批量任务与体验完善

- 完成任务队列、受控并发、批量反馈、取消排队和失败重试。

### 阶段五：交付

- 补充 README、环境变量示例、启动命令和故障排查。

- 确保仓库中没有 API Key、本机绝对配置或用户图片。

## 17. MVP 完成定义

同时满足以下条件，方可视为 MVP 完成：

- 用户能配置并持久保存两个不同的本地目录。
- 用户能安全配置 TinyPNG API Key。
- 页面能扫描、展示、搜索和筛选原图。
- 页面能准确区分待压缩、已压缩、原图已更新、结果缺失和失败状态。
- 用户能选择单张或多张图片并完成 TinyPNG 压缩。
- 结果按原相对路径自动保存到结果目录，且原图不被修改。
- 页面能展示压缩前后大小、节省比例、处理时间和错误原因。
- 关键状态、路径安全、输出写入和任务流程具有自动化测试。
- 在 macOS 和目标桌面浏览器中完成真实 API 的端到端验证。
- README 能让新的开发者或用户从零启动项目。

## 18. 默认决策与待确认事项

为使后续 AI 可以直接开始实施，未明确项暂按以下默认方案执行：

| 事项 | MVP 默认决策 | 可调整点 |
| --- | --- | --- |
| 扫描范围 | 递归扫描子目录 | 可增加关闭选项 |
| 输出结构 | 保持原图相对目录和文件名 | 可增加扁平输出或后缀命名 |
| 已有结果 | 本工具生成的同路径结果可在确认后覆盖 | 可改为自动加版本后缀 |
| 状态识别 | 持久记录 + SHA-256 + 结果存在性 | 不建议只看文件名 |
| 批量能力 | 支持多选和全部待压缩 | 可后续增加规则式自动选择 |
| 自动监控 | 第二版默认自动监听、默认不自动压缩 | 自动压缩仅处理新加入图片 |
| 支持平台 | macOS 优先 | 后续扩展 Windows/Linux |
| API 额度 | 用户自备 TinyPNG API Key | 不共享公共密钥 |
| 输出格式 | 保持输入格式 | 后续支持格式转换 |
| 再次压缩 | 允许，但需要用户确认 | 可关闭或增加强制策略 |
| 原图删除 | 不自动删除对应结果 | 后续可提供显式清理功能 |

仍建议用户在正式开发前确认以下产品偏好，但它们不阻塞按默认方案实现：

1. 第二版已实现自动监听，并以独立开关控制是否自动压缩新增图片。
2. 第二版已实现覆盖、跳过和添加后缀三种输出冲突策略。
3. 第二版已实现滑块与并排效果对比。
4. 第二版已打包为无需 Node.js 的独立 macOS 应用，仅分发 arm64 Ad Hoc 签名 ZIP。
5. 第二版只支持 Apple Silicon macOS；Intel Mac、Windows/Linux 仍属于后续版本。
6. 第二版保留任务历史和每张图片最近一次成功结果，不保留同一图片的多份历史结果文件。
